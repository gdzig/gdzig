# Godot version support: latest stable only, back-compat left to forks

gdzig supports the latest stable Godot release only. The bindings are generated from a single API snapshot of that release (`vendor/extension_api.json` / `vendor/gdextension_interface.h`). Backwards compatibility with older engine versions is left to forks (#262).

Two properties of Godot's release model drive this. First, GDExtension is forward-compatible by design within a major version: an extension built against an older 4.x API runs on newer 4.x engines (this is what `compatibility_minimum` in a `.gdextension` file declares). Tracking the latest release therefore never strands users who keep their engine current. Second, Godot has no minor-version LTS: a stable branch is guaranteed support only until the next minor's first patch release (best-effort beyond that), with long-term support existing only at major boundaries (the 3.x branch after 4.0 shipped). Anchoring gdzig to an older minor would mean committing to an engine branch whose upstream maintenance is already best-effort and on a countdown to end-of-life.

If older-engine support ever becomes a real requirement, the recorded approach is a compile-time *floor* rather than parallel snapshots: keep the single latest API snapshot and filter it downward via metadata (e.g. a `-Dgodot-version` build option), plus runtime gating. Newer-feature opt-in then works via runtime availability: interface functions are engine-supplied pointers that are simply absent on older engines, ClassDB method binds resolve by name and hash against the running engine, and gdzig already exposes the running engine version (`gdzig.version`, #158). The `@since` metadata on interface functions (in `gdextension_interface.h`) can drive generated guards that return an explicit error instead of undefined behavior when a too-new API is called on an old engine. Rare contract changes between minors — e.g. `Object.isClass` taking `String` in 4.6 and `StringName` in 4.7, with different method hashes — would need hand-written shims in one marked module, mirroring the disposable-compat-module discipline of ADR 0001.

Considered and rejected:

- **Dual API snapshots with a versioned build option (#262)**: checking in one API description per supported engine and generating bindings from the selected one. Rejected for now following the discussion in #262: it carries an ongoing cost (another snapshot to vendor, paired CI runs per engine, another engine version to keep in mind for every change) in support of an older engine branch whose upstream maintenance is best-effort and time-limited. Parts of #262 remain salvageable on their own merits: the test-runner fixes, and the loader's `@since` check before requesting optional interface functions.
- **Supporting a sliding window of recent minors** (latest plus N-1, N-2): rejected; Godot guarantees branch support only until the next minor's first patch, so any window wider than the latest stable rests on best-effort upstream maintenance and soon includes abandoned branches, and each additional minor multiplies CI and compat surface.
- **Treating latest-generated bindings as implicitly back-compatible**: rejected; building against the latest API does not make the result run on older engines, and pretending otherwise surfaces as missing interface pointers and unresolved method binds at runtime rather than a clear signal at build time.
