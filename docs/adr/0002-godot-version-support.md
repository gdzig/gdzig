# Godot version support: single latest API snapshot, backwards compatibility via runtime discovery

gdzig generates bindings from a single API snapshot of the latest stable Godot release (`vendor/extension_api.json` / `vendor/gdextension_interface.h`). Backwards compatibility with older engines within the same major version is supported at runtime, by discovery rather than build-time variation: the same compiled extension binds against whatever engine version loads it.

Two properties of Godot's release model drive this. First, GDExtension is forward-compatible by design within a major version, and Godot maintains `hash_compatibility` metadata in the API description for exactly this reason: `classdbGetMethodBind` accepts compatibility hashes, so a method bind that fails under the latest hash can fall back to the hash the running engine actually serves. Second, Godot has no minor-version LTS: a stable branch is guaranteed support only until the next minor's first patch release (best-effort beyond that), with long-term support existing only at major boundaries (the 3.x branch after 4.0 shipped). Build-time version targeting would mean snapshotting engine branches whose upstream maintenance is on a countdown to end-of-life; runtime discovery covers them from the one latest snapshot instead.

Concretely, most signature changes between minors need no shim at all: additive trailing arguments are safe (ptrcall passes no argc, so an older-layout bind simply never reads the extra slots), as are ABI-identical enum moves. The exceptions are methods whose compatibility bind speaks the old argument *layout*; those get runtime-version-gated marshaling keyed off the engine version on the dispatch table (never a compile-time flag), behaving correctly on both engines. #265 is the first application of this policy (Godot 4.6 runtime support): the 27 methods with changed hashes route through the `hash_compatibility` entries emitted by bindgen, and the 3 layout-incompatible methods (`Object.is_class`, `RichTextLabel.add_image`, `RichTextLabel.update_image`) get gated shims. Reverse-direction cases — engine-called virtuals with changed signatures — are documented as latest-only rather than shimmed.

Considered and rejected:

- **Dual API snapshots with a versioned build option (#262)**: checking in one API description per supported engine and generating bindings from the selected one. Rejected following the discussion in #262, and superseded by runtime discovery, which covers the 4.6/4.7 delta from the single latest snapshot with no vendored older API and no build option. Parts of #262 remain salvageable on their own merits: the test-runner fixes, and the loader's `@since` check before requesting optional interface functions (`@since` lives on interface functions in `gdextension_interface.h`).
- **Compile-time floor** (filter the latest snapshot downward via a `-Dgodot-version`-style build option): rejected; it splits the build and test matrix per engine version for a problem runtime discovery solves without any build-time switching.
- **Treating latest-generated bindings as implicitly back-compatible without shims**: rejected; the small number of layout-incompatible signature changes would misread memory on older engines. The runtime gates exist precisely for those cases.
